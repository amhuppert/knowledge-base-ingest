# Codex review of the KB tooling implementation plans

Scope: `docs/plans/00-overview.md` through `07-skills-and-evaluation.md`, checked
against the current implementation, migrations, repositories, schemas, and tests.
The current baseline is healthy (`pnpm test`: 99 tests passed; `pnpm typecheck`:
passed), so the findings below concern the proposed plan rather than an already
failing tree.

Three important premises were verified and do not need redesign:

- `Repositories.tx()` is exactly `db.transaction(fn).immediate()`
  (`src/db/repositories/index.ts:38-41`). better-sqlite3 11.10 uses nested
  savepoints, and an outer sentinel throw rolls back inner service transactions.
- The FTS5 tables are maintained by SQLite triggers
  (`src/db/migrations.ts:199-240`). A nested transaction probe confirmed that an
  outer rollback removes both the content rows and the trigger-created FTS rows.
  The basic dry-run rollback mechanism in Phase 1 §2 is therefore sound.
- Per-scope fallback is mechanically feasible: the current query module already has
  separate chunk/claim/node helpers and all three FTS tables use Porter tokenization.
  The problems are the public match/rank/result contracts identified below, not the
  decision to perform fallback independently for each scope.

## Findings

1. **blocker — `01-shared-contracts.md` §1 and §4; `02-phase-0-contract-and-baseline.md` §1 (custom help).** Commander v14 treats the proposed custom `--help` as an ordinary boolean. It checks mandatory options and required positional arguments before invoking the action, so `runAction()` cannot short-circuit first. Commands such as `kb ingest --help --json`, `kb claim conflict --help --json`, and any `--file` command declared with a mandatory option will fail with a usage error instead of returning a HelpSpec. **Recommended fix:** add an explicit pre-parse help router in `index.ts`/an exported `runCli(argv, io)` that resolves a known command path and emits its HelpSpec before `parseAsync`; alternatively declare all arguments/options optional in Commander and perform a shared pre-action usage validation, still returning exit 2. Add a table-driven test that requests help from every leaf while omitting all otherwise-required inputs.

2. **blocker — `01-shared-contracts.md` §1 and §5; `02-phase-0-contract-and-baseline.md` §1 (bare root/groups and unknown commands).** The bare-help design conflicts with Commander’s dispatch rules. With no parent action, bare `kb`/`kb node` invokes Commander-generated help as an error (exit 1), even with `.helpOption(false)`. Adding a parent action makes misspellings such as `kb nodee tree` or `kb node frob` reach that action and surface as `commander.excessArguments`, not `unknownCommand`, so suggestions disappear. Also, merely omitting `.addHelpCommand()` does not disable Commander’s implicit `help [command]`. **Recommended fix:** pre-route only the exact empty-root and exact known-group invocations, leave Commander parents actionless for unknown-command detection, and call `.helpCommand(false)` on root and groups. Test `kb`, `kb node`, `kb nodee tree`, `kb node frob`, and `kb help` together, including exit codes and absence of raw Commander help.

3. **major — `01-shared-contracts.md` §1 lines 63-70 (standard-option placement).** “Options are registered per-leaf … so flag position never matters” is false. Leaf-only options accept `kb source list --json`, but reject `kb --json source list` and `kb source --json list`; the current hand parser accepts all three. If the group also registers `--json`, Commander consumes it on the group and a leaf’s `opts()` still does not contain it unless global/ancestor options are merged deliberately. **Recommended fix:** either narrow the public contract to “standard flags may appear anywhere after the complete leaf command path,” or specify argv normalization/global options plus `optsWithGlobals()` and duplicate precedence. Add a position matrix for `--json`, `--kb`, `--help`, and `--dry-run`, including `--` handling.

4. **major — `02-phase-0-contract-and-baseline.md` §2 (`--version`).** Commander’s `.version()` cannot implement `kb --version --json`: it writes the plain version and exits during option parsing, before a later `--json` is handled, and it cannot return the rich version payload. **Recommended fix:** explicitly prohibit `.version()` and route the ordinary root `--version` flag through the same pre-parse/custom handler as `kb version`. Test both flag orders and assert one envelope, no raw version text, and exit 0.

5. **major — `01-shared-contracts.md` §1 and §3 (Commander setup and error mapping).** The setup is not exhaustive enough for Commander v14. Reachable codes include `missingArgument`, `optionMissingArgument`, `missingMandatoryOptionValue`, `invalidArgument`, `excessArguments`, `conflictingOption`, `unknownOption`, and `unknownCommand`; the plan does not decide codes for excess/conflicting inputs. `InvalidArgumentError` from an arg parser is caught and rethrown by Commander as a plain `CommanderError` with code `commander.invalidArgument`, so an `instanceof InvalidArgumentError` trap is insufficient. In addition, `exitOverride`, output configuration, and disabled help are copied when `parent.command()` creates a child and are not retroactively inherited; `addCommand(new Command())` does not copy them. **Recommended fix:** define an exhaustive `CommanderError.code -> IssueCode` table, configure the root before registration or recursively configure the final tree, and prescribe one command-construction API. Add a nested-leaf test for every reachable code that proves no `process.exit` or raw stderr occurs.

6. **major — `01-shared-contracts.md` §1 (missing option values).** Commander greedily accepts another option token as the required value of a string option: `--kb --json` produces `kb: "--json"` and loses JSON mode, while `node create --title --json --kind root` can create a node literally titled `--json`. This violates the “nothing silently coerced or ignored” rule. **Recommended fix:** add a shared pre-scan/string parser that treats a recognized option token as a missing value, with an explicit `--flag=--literal` escape if dash-prefixed values must be supported. Test `--kb --json`, `--file --json`, `--title --json`, and `--text-from --dry-run`.

7. **major — `01-shared-contracts.md` §1 and §7; `02-phase-0-contract-and-baseline.md` §1 (positional/stdin compatibility).** Strict Commander declarations leave current behavior unresolved. `search` and `ask-context` currently join all remaining positionals (`src/cli/index.ts:434-448`), so unquoted multiword input works; a single `<query>` declaration would reject it as excess arguments. `claim conflict` is variadic. Payload commands currently read stdin when `--file` is absent or `-` (`src/cli/index.ts:71-75`), so making `--file` mandatory breaks existing tests and parity. **Recommended fix:** declare `<query...>`, `<question...>`, and `<claim_id...>` explicitly, and document `--file <path>` as optional with stdin/`-` as the default. If any behavior is intentionally broken, list it in a compatibility table rather than claiming identical semantics.

8. **major — `01-shared-contracts.md` §1 and §7 (CLI runner testability).** The proposed parse-error trap lives in `index.ts` and scans `process.argv`, while the planned tests call `buildProgram().parseAsync(testArgs)`. Those tests bypass the trap and inspect the wrong argv for JSON mode. The current `src/cli/index.ts` also self-executes and exports no dispatcher; current CLI tests are subprocess/temp-directory tests, not an in-memory dispatcher. **Recommended fix:** first extract `runCli(argv, {stdout, stderr, cwd, env}) -> Promise<number>` containing raw-token detection, parse/error mapping, emission, and exit-code reset. Make both `index.ts` and in-process tests call it, and retain at least one subprocess smoke test for `bin/kb`.

9. **blocker — `01-shared-contracts.md` §2-§3 (`verify --strict`).** The envelope invariant `ok === issues.every(i => i.severity !== "error")` cannot represent current strict verification. `verify()` intentionally returns `ok:false` when it has only warning findings such as `no-stale-nodes` (`src/verify/verify.ts:174-196`). Keeping that finding as a warning issue forces envelope `ok:true`; changing the data finding to error breaks its legacy meaning. **Recommended fix:** in strict mode, preserve `data.findings[].severity` but create error-severity envelope issue copies (or define a separate explicit policy-failure field and revise the invariant). Add strict and non-strict envelope tests for a warning-only KB.

10. **major — `01-shared-contracts.md` §2; `03-phase-1-preview-and-receipts.md` §3; `04-phase-2-corpus-batching.md` §§1-3; `05-phase-3-retrieval-and-answer-check.md` §§1 and 4; `06-phase-4-lineage-and-coverage.md` §§1 and 3 (envelope shape).** The examples mix envelope fields into command data. `issues`, `nextActions`, and `hints` are defined as top-level envelope fields, but receipts place them beside `claims`, `nodes`, or `findings`; the answer-check example also has an `ok` that could be either the envelope or `data.ok`. Current `render --check`, `verify`, and `answer-check` can fail with useful non-null data, while the plan never defines a constructor for “failed envelope with data.” **Recommended fix:** specify exact `success(data, issues?)` and `result(data, issues)` constructors, normalization/derivation order, and root-warning merging. Rewrite every sample as a complete envelope, keeping command data under `data` and top-level guidance/issues in the envelope. State explicitly whether coverage findings live in `issues`, `data.findings`, or both.

11. **major — `01-shared-contracts.md` §2 and §7; `03-phase-1-preview-and-receipts.md` §3; `05-phase-3-retrieval-and-answer-check.md` §4; `06-phase-4-lineage-and-coverage.md` acceptance (parity is not additive).** Phase 0 says old fields keep their exact meaning and parity permits only additive envelope fields, but Phase 1 replaces current claim/graph/synthesis shapes (`claimsCreated`, `entitiesCreated`, `updated`, etc.), ingest omits current `updated`/`next`, and Phase 4 removes `uncitedSentences`. `toMatchObject(golden)` will fail once those fields disappear. **Recommended fix:** add a command-by-command compatibility matrix. Retain deprecated aliases for the envelope-v2 compatibility window, or explicitly version each breaking payload and limit the “additive only” promise to Phase 0. Keep `uncitedSentences` for v2 or tie removal to a documented major version, not merely “one phase.”

12. **major — `01-shared-contracts.md` §2-§3; `03-phase-1-preview-and-receipts.md` §1 and deliverable 6 (issue registry and domain errors).** `LEGACY` must be emitted in Phase 0 but is absent from the registry, while the registry snapshot is additive-only; removing the registry entry in Phase 1 would itself violate that rule. The mechanical verify mapping also invents semantically duplicate codes (`CITATION_RESOLVES`, `PARENT_CITES_SUBTREE`, `CITATION_ACTIVE`) instead of the already-defined `CITATION_UNKNOWN`, `CITATION_OUT_OF_SUBTREE`, and `CITATION_INACTIVE`. Existing service errors are plain message-only subclasses/generic `Error`s, so mapping them by message would be brittle. Finally, a domain service returning `Issue` from `src/cli/issues.ts` reverses the current domain-to-CLI dependency direction. **Recommended fix:** keep `LEGACY` registered but assert it is no longer emitted; define an explicit verify-check map reusing semantic codes; introduce a domain-level typed diagnostic/error with code, path, ids, and details; and map it to CLI `Issue` at the boundary.

13. **major — `01-shared-contracts.md` §1-§4 (incomplete error details).** The “every failing error has a hint” gate has no concrete hint for `INTERNAL` or the verify checks, and some generic unknown-ID recovery commands do not exist (`claim list`/`entity list`). Zod paths are shown as `claims[2].spans[0].quote`, described as dot-joined in `runAction`, and prefixed as `nodes[i]` in Phase 2. `PAYLOAD_PARSE_ERROR` promises a byte offset, but `JSON.parse` reports a UTF-16 character position, not a byte offset. **Recommended fix:** provide a per-code hint registry using only legal commands, choose one canonical path serializer, and either report a character offset or convert it with `Buffer.byteLength(raw.slice(0, position), "utf8")`. Add non-ASCII malformed JSON and every-hint-validity tests.

14. **major — `00-overview.md` dependency order; `01-shared-contracts.md` §5-§6; `03-phase-1-preview-and-receipts.md` §6; `04-phase-2-corpus-batching.md` acceptance; `06-phase-4-lineage-and-coverage.md` dependency declaration (phase-illegal steering).** Phase 0 global help advertises `node apply`, and shared/Phase 1 stale steering emits `node show --context`, although both arrive only in Phase 2. Phase 2 then says to “flip” a Phase 1 placeholder that Phase 1 never actually defines. Phase 4 declares only a Phase 1 dependency while using Phase 2 steering and removing a Phase 3 field. **Recommended fix:** make each phase expose only commands available at that phase, name the Phase 1 placeholder explicitly, and declare Phase 4 dependent on Phases 1-3 (or move cross-phase cleanup to a final integration phase). Add phase-level command-registry tests that validate every emitted command.

15. **major — `01-shared-contracts.md` §6; `03-phase-1-preview-and-receipts.md` §6; `06-phase-4-lineage-and-coverage.md` §4 (steering rules contradict actual state transitions).** “Any mutation with zero stale nodes -> verify, render” conflicts with per-command flows: init should ingest/build structure, ingest should inspect chunks, node apply may need ingestion, and graph apply never stales nodes (`src/domain/services/graphService.ts`). Phase 4 nevertheless sends graph apply to a stale-context chain. Its “first render when no prior rendered files” condition is unreachable in the normal workflow because current `init` renders immediately and populates `rendered_files` (`src/cli/index.ts:235-244`). **Recommended fix:** replace the global zero-stale rule with an explicit per-command precedence table; remove graph from stale steering unless graph-to-node dependencies are added; and define “first post-content render” from pre-render source/node state or remove the special case.

16. **major — `00-overview.md` lines 42-58; `01-shared-contracts.md` §2 and §6; command examples in `03-phase-1-preview-and-receipts.md` through `06-phase-4-lineage-and-coverage.md` (copy-pasteable actions).** `NextAction.command` is promised to be complete and executable, but examples contain `<path>`, `<payload.json>`, and filenames that may not exist. A dry-run read from stdin also cannot emit “the same command without `--dry-run`” without preserving the payload somewhere. **Recommended fix:** keep `NextAction` for commands composed entirely from known IDs/paths; introduce a separate typed template/advice field with `requiresInput`, or move placeholder commands to hints. For stdin previews, require a file-backed payload before offering a replay command, or return the validated payload in a safe receipt field.

17. **major — `00-overview.md` Phase 1 summary; `03-phase-1-preview-and-receipts.md` goal/deliverables (dry-run scope).** “`--dry-run` everywhere” and “every mutation can be previewed” are not what the deliverables implement. `init`, `node create`, `claim conflict`, `claim supersede`, `propagate`, and `render` remain mutations without dry-run, and `node apply` waits until Phase 2. **Recommended fix:** narrow the normative statement to the authored apply/ingest/synthesis payloads and list them exhaustively, or specify dry-run behavior for every mutation. Align HelpSpec `supportsDryRun`, skills, and acceptance wording with the chosen scope.

18. **major — `03-phase-1-preview-and-receipts.md` §2, §6, and acceptance (dry-run receipt parity).** A successful dry run is specified to steer to the real apply command, while the real apply steers to stale-node synthesis or verify/render. Therefore the promised “dry-run receipt equals the subsequent real receipt minus `dryRun`” cannot hold. State-dependent fields such as timestamps or generated actions may differ too. **Recommended fix:** define a comparison projection containing only deterministic domain receipt fields and explicitly exclude `dryRun`, `nextActions`, `hints`, and clock-derived fields. Add separate assertions for preview steering and post-commit steering.

19. **blocker — `03-phase-1-preview-and-receipts.md` §5 (source-store cleanup API).** The cleanup algorithm cannot be implemented against the actual `SourceStore`. `relPath()` is private, `store()` returns a path only after potentially creating the file, and neither `FsSourceStore` nor `MemorySourceStore` has a removal operation (`src/ingest/sourceStore.ts:14-20, 26-31, 43-88`). A naïve `existedBefore` check is also race-prone: a losing concurrent ingest could delete a file now referenced by the winner. **Recommended fix:** make `store` return `{storedPath, created}` using atomic create semantics, add `remove(storedPath)` to both stores, and recheck duplicate state while holding the DB write lock before storing. Test newly-created, pre-existing, injected DB failure, cleanup failure, and concurrent same-source commits.

20. **major — `03-phase-1-preview-and-receipts.md` §5 (prepare/preview/commit split).** `prepare()` is called pure, but dry-run must query `getBySha256` to report `new|duplicate` and preview metadata updates. Current duplicate detection occurs before decoding (`src/domain/services/ingestService.ts:35-64`), so moving decode into unconditional prepare also changes duplicate behavior despite “unchanged public behavior.” A duplicate checked only before `BEGIN IMMEDIATE` remains vulnerable to concurrent unique-key failures. **Recommended fix:** specify three exact stages: pure `prepareContent(input)`, read-only `plan(prepared, repos)`, and `commit(plan)` that rechecks SHA/canonical text inside `BEGIN IMMEDIATE`. State whether validation precedes duplicate recognition and test both orderings and a concurrent duplicate.

21. **major — `03-phase-1-preview-and-receipts.md` §3.1 and §4 (claim no-op implementation).** The proposed existence check is circular: it says to check the span before `resolveSpan`, but only “after offset resolution,” while current `resolveSpan()` both calculates offsets and writes (`src/domain/services/spanResolver.ts:18-59`). In a mixed updated input, blindly upserting every link can also lower an existing `claim_spans.confidence`, because the current upsert overwrites rather than takes the maximum (`src/db/repositories/provenance.ts:41-50`). **Recommended fix:** split pure `resolveSpanCandidate()` from persistence, inspect span/link state from the candidate, write only new or confidence-improving rows, and define link-created/reused accounting for different roles. Test mixed new/reused refs and a lower-confidence replay.

22. **major — `03-phase-1-preview-and-receipts.md` §3.2 and §4 (graph schema/receipts).** “Same pattern” overlooks accepted but discarded data. `EntityInputSchema` accepts `evidence`, yet `GraphService` ignores it and there is no `entity_spans` table; relationship evidence accepts confidence, but `relationship_spans` has no confidence column and the service drops it (`src/domain/schemas/agent.ts:55-70`, `src/domain/services/graphService.ts:85-123`, `src/db/migrations.ts:171-178`). The service can label a relationship unchanged, then add evidence, and always writes a changelog row. **Recommended fix:** either remove/reject unsupported evidence fields with a documented compatibility change, or specify the required migrations and persistence. Define evidence-only changes as `updated`, define exact-repeat graph changelog behavior, and add per-input evidence/accounting tests.

23. **major — `03-phase-1-preview-and-receipts.md` §1 and §4 (synthesis semantics).** The validator does not define deterministic output when a citation is both inactive and outside the subtree (one issue or both, and in what order). “Stale-cleared flips `is_stale` only” conflicts with the only current helper, which also changes `updated_at` (`NodeRepo.setStale`, `src/db/repositories/synthesis.ts:96-100`). The plan also does not decide whether changing a child title/summary/body marks ancestors stale even though those values are parent context/render inputs. **Recommended fix:** specify validation precedence/order; add a dedicated `clearStale` with explicit timestamp semantics; and state ancestor-staleness rules for synthesis changes. Test the cross-product of stale/content/title/summary and parent state.

24. **major — `04-phase-2-corpus-batching.md` §2 (hierarchy replay).** Prevalidation says a `(parent, slug)` collision with an existing child is `DUPLICATE_SLUG`, while exact replay must return `existing`. Every replay necessarily has that collision because node ID is derived from `(parent, slug)` (`src/domain/algorithms/idDeriver.ts:72-75`). Counting an existing root plus its replay spec as two roots creates the same contradiction. **Recommended fix:** reserve `DUPLICATE_SLUG` for two distinct manifest locations; resolve a DB collision to its derived node ID, return `existing` when title/kind match, and emit the mismatch codes otherwise. Count distinct logical root IDs, not “existing row + manifest entry.” Add replay tests including the root.

25. **major — `04-phase-2-corpus-batching.md` §1 (context completeness/determinism).** The “synthesis-ready” context removes `bodyMd`/`bodyHash` from the node shape even though current `node show` returns the full node and an agent needs the existing body to revise it. `approxTokens = ceil(JSON.stringify(data).length/4)` is self-referential because `data` contains `approxTokens` and, in the examples, envelope steering. Depth/sortOrder/createdAt are not total ordering keys; source, provenance, and citation-ID ordering are unspecified. **Recommended fix:** include current body/hash, define the exact subset measured before adding `stats`, and add final tie-breakers (`nodeId`, `claimId`, `sourceId`, span ID). Specify one batched provenance SQL query and test equal-key ties.

26. **major — `02-phase-0-contract-and-baseline.md` §4.2; `04-phase-2-corpus-batching.md` §3-§4 (baselines and order tests).** The scripts are not mechanically comparable as written. `render --check` after mutations fails unless a real `render` occurred first. Old and new flows necessarily have different changelog rows/command grouping, so raw DB or rendered changelog/index bytes cannot be identical even when domain state is equivalent. The proposed deepest-first test is vacuous: a parent citing a pre-existing child claim succeeds regardless of synthesis execution order. **Recommended fix:** run `render` before `render --check`; compare an explicitly normalized semantic snapshot that excludes changelog/timestamps/render bookkeeping; and assert batch application order through injected timestamps, changelog order, or a service spy, including equal-depth input order.

27. **major — `05-phase-3-retrieval-and-answer-check.md` §1 (`--match` semantics).** `--match all` is defined as AND followed by automatic OR fallback, but the fallback hint says to use `--match all` “to require all.” There is no strict-AND mode. The all-zero hint recommends `--match any` even though the identical OR query already ran. **Recommended fix:** add `auto` as the default fallback mode and make `all` strict AND, retaining `any|phrase`; or explicitly state that strict AND is unavailable and remove the false hints. Update the skill and tests to match one definition.

28. **major — `05-phase-3-retrieval-and-answer-check.md` §1 (search result/rank contract).** Acceptance requires `rank` in every hit, but entity hits remain LIKE-based and have no FTS rank. Raw BM25 values from three separate indexes are not globally comparable, while current `scope=all` concatenates scopes (`src/query/query.ts:57, 157-175`). Current `search()` returns only `SearchHit[]`, which cannot report a fallback mode for a zero-hit scope. **Recommended fix:** define `SearchResult {hits, matchModes, hints}` and per-scope helper results; make entity rank absent or `null`; define scope ordering and require rank ordering only within each FTS scope. Export a runtime `SEARCH_SCOPES as const` rather than trying to source Commander choices from the erased `SearchScope` type.

29. **major — `05-phase-3-retrieval-and-answer-check.md` §2 (ask-context filters).** Intersecting subtree/type after the current `limit * 4` fetch can produce false zeroes when qualifying claims rank below excluded rows (`src/query/query.ts:243-258`). The zero hint always tells users to remove `--claim-type`, even if only `--node` is active, and unknown-node behavior is not assigned an issue. **Recommended fix:** validate the node first, push surfaced status, claim type, and recursive subtree predicates into SQL before `ORDER BY/LIMIT`, and construct hints from the filters actually supplied. Add a regression with more than `4 * limit` higher-ranked excluded claims.

30. **major — `05-phase-3-retrieval-and-answer-check.md` §3 (acceptance gate).** The retrieval threshold is called an acceptance test, but failure may also complete the phase via an unspecified “evidence package.” No artifact path, schema, waiver authority, or mandatory next increment is defined. **Recommended fix:** either make `>=7/8` and `<=1` a hard gate, or define the exact evidence file and the automatic follow-on decision (for example `docs/plans/retrieval-phase3-results.json` causing a required stop-word Phase 3b). Do not label both an unmet gate and a passing phase.

31. **major — `05-phase-3-retrieval-and-answer-check.md` §4 (Markdown scanner and line numbers).** The proposed `lineMap` cannot be used with the current splitter, which mutates text and returns strings without offsets (`src/query/query.ts:303-307`). Footnote continuation (“indented >=2 spaces or until blank”), fence length/indent/closure, multi-backtick inline code, escaped/unmatched quotes, and unclosed fences are unresolved. Tracking quotes only to suppress splitting also does not make an ordinary inline exact quotation non-assertive, despite the stated “exact quotations never trigger” goal. **Recommended fix:** specify a state machine that returns sentence spans `{text,startOffset,endOffset}`, define every opener/closer and EOF rule, and map the span start to the original line. Add tests for immediate unindented prose after a footnote, tilde/unclosed fences, multi-backtick code, escaped/unmatched quotes, identical sentences on different lines, and ordinary quoted questions.

32. **major — `05-phase-3-retrieval-and-answer-check.md` §4 (citation extraction regions).** Extracting citations from the entire original text validates citation-shaped examples inside fenced/inline code, so `[^clm_deadbeef]` in a code sample becomes `CITATION_UNKNOWN` even though that region was stripped as non-assertive. Separately, the current shared global regex is stateful: `hasCitation()` leaves `lastIndex` nonzero and can cause the next `extractCitations()` call to miss a citation (`src/domain/algorithms/citations.ts:7-22`). **Recommended fix:** have the Markdown pass return retained citation regions plus captured footnote-definition IDs, explicitly excluding code; use separate/non-global regexes or reset state at the start of extraction. Add code-token and reverse-call-order regressions.

33. **major — `05-phase-3-retrieval-and-answer-check.md` §4; `06-phase-4-lineage-and-coverage.md` acceptance (answer-check result compatibility).** The plan does not say whether unknown/inactive citations produce one issue per ID or aggregate issues, how issues are ordered relative to uncited sentences, or where the nested result’s `ok` lives. Removing `uncitedSentences` one phase later is an abrupt, unrelated breaking change. **Recommended fix:** provide one complete failing envelope with `data:{ok,citedClaims,unknownCitations,inactiveCitations,uncited,uncitedSentences}` and deterministic one-per-ID/one-per-sentence issue ordering; retain the deprecated field for all of envelope v2.

34. **blocker — `06-phase-4-lineage-and-coverage.md` §1 (extractor representation).** The plan stores a free-form `name/version` in `source_texts.extractor`, but the actual table/model require separate `extractor TEXT` and `extractor_version INTEGER` (`src/db/migrations.ts:45-52`; `src/domain/schemas/models.ts:27-33`). The allowed regex permits non-integer versions, and the claimed native `cli/1` is factually wrong: current native normalization is `text-utf8/1` (`src/domain/algorithms/normalize.ts:19, 28-29`). **Recommended fix:** since Phase 4 says no migration, constrain the flag to `name/<decimal integer>`, split it into the two existing columns, and recombine for display. Otherwise add an explicit migration/model/repository plan for textual versions. Align metadata `method` with the chosen representation.

35. **blocker — `06-phase-4-lineage-and-coverage.md` §1 (corrected sidecar identity).** The suggested recovery “ingest the corrected transcription as a new version using `--supersedes`” cannot create a new source from the same original: ID derives solely from original bytes, and both ID and full SHA are unique (`src/domain/algorithms/idDeriver.ts:34-37`; `src/db/migrations.ts:25-40`). `--supersedes` does not change identity. **Recommended fix:** state that the same original plus different canonical text is always rejected, even with `--supersedes`; make the executable correction recipe ingest the corrected transcription file itself as a byte-distinct UTF-8 source that supersedes the derived-source record, or explicitly redesign derived-source identity. Test the exact documented recipe.

36. **major — `03-phase-1-preview-and-receipts.md` §5; `06-phase-4-lineage-and-coverage.md` §1 (native media and UTF-8 behavior).** “Current path unchanged” conflicts with the recipe’s apparent four-extension allowlist. Current CLI maps unknown extensions to `text/plain` and accepts any non-PDF, NUL-free bytes; it does not actually detect malformed UTF-8 because `Buffer.toString("utf8")` substitutes replacement characters (`src/cli/index.ts:56-64`; `src/domain/services/ingestService.ts:127-134`). **Recommended fix:** choose an exact policy. To preserve compatibility, accept any known-text or unknown-extension input that passes `TextDecoder("utf-8",{fatal:true})` and contains no NUL, while known binary extensions require a sidecar. List the complete MIME map rather than “analogous,” and test malformed UTF-8 and unknown extensions.

37. **major — `06-phase-4-lineage-and-coverage.md` §1-§2 (metadata/defaults/duplicates).** The plan leaves implementer choices for the default `--verification`, `--extractor` without a sidecar, duplicate metadata merge versus replace, same canonical text with a different extractor/raw sidecar hash, and `updated` accounting. `SourceRepo` has no metadata update API. Validating `.strict()` “on every write” can also reject legacy/unknown metadata unless ownership is defined. **Recommended fix:** specify `verification=none`; reject extractor/verification without `--text-from` as a pre-workspace usage error (exit 2); make normalized canonical `textHash` the immutability key; keep first-write extraction provenance immutable; patch-merge supplied origin fields; and define how unknown existing keys are preserved or migrated. Add a duplicate-update matrix.

38. **major — `06-phase-4-lineage-and-coverage.md` §3 (coverage query semantics).** `CHUNK_UNCITED` says claim or graph evidence but its sketch counts any overlapping span. Deleting a claim/relationship removes the link and leaves the span, so orphan spans falsely make a chunk covered. Half-open overlap, status treatment, finding cardinality/order, cap metadata, and summary units are not specified. `NODE_SINGLE_SOURCE` is also ambiguous between directly owned claims, subtree claims, and claims actually cited in the node body. **Recommended fix:** provide exact queries using live `claim_spans`/`relationship_spans` links and `sp.char_start < chunk.char_end AND sp.char_end > chunk.char_start`; define active/conflicted/historical treatment for every check; measure node support from cited claims if that is the intended concept; and specify stable ordering plus `{shown,total,omitted}` for caps. Add orphan-only, inactive-only, relationship-only, and cap-boundary tests.

39. **major — `02-phase-0-contract-and-baseline.md` §4.1; `06-phase-4-lineage-and-coverage.md` §3 (coverage fixture/output/recovery).** “One source section left claim-less” cannot trigger source-level `SOURCE_NO_CLAIMS`; each listed fixture source has a claim payload, so it only creates uncited chunks. Coverage codes are declared info issues, but the sample puts them only in `data.findings`. The hint recommends retiring a source via a status change, yet no source-status/retire command exists. **Recommended fix:** add a whole active fixture source with no claim links; decide whether findings are top-level issues or data and make the example complete; remove the nonexistent retirement advice or fully specify a source-retire command.

40. **major — `02-phase-0-contract-and-baseline.md` §1-§3 (factual inventory/exact outputs).** The source has 21 leaf handlers, not 18. The exact version example says schema 3 although the migration set’s `currentSchemaVersion()` is 1 and no planned phase adds a schema migration. `source list` does not say whether `counts` reflect the status filter or all sources, and ordering by `ingestedAt` alone is not deterministic on ties (current repo uses `ingested_at, id`). **Recommended fix:** derive command/spec completeness from the registry, show the dynamic schema value (currently 1), define filtered/global count semantics, and order by `(ingestedAt,id)`. Add missing/older/too-new read-only version probes and source-list tie/filter tests.

41. **major — `07-skills-and-evaluation.md` §3 and acceptance (evaluation reproducibility).** The repository has no `skills-v0` tag. Stages 2 and 3 depend on prior KB state, but the plan does not say whether each old/new run uses its own cumulative stage output or a shared deterministic seed. Model/version/settings, transcript command counting, and retry classification are also unspecified. The efficiency gate can punish success: an old skill that fails early may use fewer commands than a revised skill that passes, making `revised <= old` impossible; “gate met or misses documented” is not a shipping gate. **Recommended fix:** check in immutable old skill copies or pin an exact commit, define a seed snapshot for every paired stage, record exact model/settings and scoring rules, require terminal correctness first, and compare efficiency only when both variants pass. State whether a miss blocks release.

42. **minor — `07-skills-and-evaluation.md` §4 (documentation generation).** The target skill paths and generator import mechanism are omitted. The actual skills are under `.claude/skills/*/SKILL.md`; plain `node scripts/gen-command-docs.mjs` cannot directly import TypeScript HelpSpec modules without a loader/build, and tracked `docs/index.html` is not mentioned. **Recommended fix:** name every input/output path, have the generator invoke the CLI’s JSON help or run under `tsx`, use idempotent generated-section markers, and state whether `docs/index.html` must be regenerated.

## Overall verdict

The direction is strong, and the core SQLite/savepoint/FTS rollback premise is
technically sound. The documents are not yet decision-complete. Implementation is
blocked most directly by Commander help dispatch, strict-verify envelope semantics,
the missing source-store cleanup contract, the extractor-column mismatch, and the
impossible same-original sidecar correction flow. Resolving those blockers plus the
receipt compatibility, steering, retrieval, Markdown, coverage, and evaluation
ambiguities above would make the plan mechanically implementable without reopening
the protected architecture decisions.
